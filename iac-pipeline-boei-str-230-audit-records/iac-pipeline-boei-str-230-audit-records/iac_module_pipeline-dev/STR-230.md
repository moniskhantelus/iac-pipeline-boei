# STR-230 implementation and deployment notes

## What changed

The supplied outer ZIP contained this nested pipeline template repository, not an infrastructure module. The original init job repeatedly ran init, masked errors with `|| true`, and never ran plan. The original apply job only initialized Terraform; its apply command was commented out. This change runs plan once, stores the binary plan and full text output, and applies that exact saved plan once. This enables the story's intended apply behavior; it is a material correction to the supplied baseline.

Plan/apply artifacts use `when: always` and `expire_in: 90 days`. Failed commands retain their exit status. The apply job explicitly downloads init artifacts. Branch rules, stages, images, scan jobs, manual gate placement, destroy behavior, state naming and infrastructure service-principal authentication remain as supplied. The existing approval gate is AFTER apply; it has not been moved. Removed credential echo lines and an embedded commented state key from edited jobs; rotate any previously exposed credentials through the organization's process.

Audit uses an isolated Azure CLI profile and managed identity, leaving infrastructure credentials unchanged. Unique blob names plus conditional, non-overwriting block uploads prevent accidental replacement. The custom writer role grants write only, no delete or policy-management rights. Reader access is separate. The unlocked 730-day policy is a draft: administrators can change/remove it. It is NOT yet the legally approved administrator-proof compliance record.

`iac/.audit_runtime.yml` embeds `scripts/audit.py` because GitLab cross-project includes do not copy runtime files into module checkouts. Keep both synchronized; the test enforces this. Consumers using the supplied workflow receive the new include automatically. Consumers directly including individual job files must also include `/iac/.audit_runtime.yml` from the same reviewed ref.

## Provisional 11-field contract — S010 dependency

S010 and the complete blueprint were not supplied. Do not claim exact S010 conformance until its owner approves this mapping. Fields are: `actor` (GitLab login/ID), `commit_sha`, `plan_hash` (SHA-256 of the actual saved binary plan), `timestamp` (UTC completion/record time), `environment` (override or branch prefix), `module` (override or project path), `outcome` (`success`/`failure`), `pipeline_id`, `job_id`, `pipeline_url`, `exit_code` (integer). Missing upstream metadata is JSON null; a setup failure before a plan exists has a null hash. A refused/missing-plan apply is a failure. Job setup failures use exit code 1 as a sentinel, not the original command code.

The main wrapper publishes after success/failure and retains local JSON if Azure is unavailable. Upload failure fails an otherwise successful job; a failed Terraform exit code is preserved. `after_script` creates a failure record if setup failed before the wrapper. GitLab does not propagate after-script failures, but setup failures already fail the job. Cancellation, forced runner termination, timeout, network loss, or GitLab artifact upload failure cannot be guaranteed by an in-job hook. Operations must monitor failed/missing audit uploads, recover retained JSON without replacing existing blobs, and reconcile pipeline/job IDs against the audit store. Infrastructure may have succeeded when an audit upload fails: inspect state before rerunning.

## Deployment dependencies

1. Deploy `shared-services/audit` independently in the shared-services subscription with a dedicated backend (supply backend configuration), RG/account name, location, existing state-account name, runner MI principal ID, reviewer principal ID and allowed subnets. The account must be distinct from ALL state accounts; the input check verifies the supplied name only. Subnets need Microsoft.Storage service endpoints and reviewer/deployment network reachability. Verify regional GRS support. Deployment operator needs resource/role/policy permissions and data-plane access for container creation.
2. Attach an existing system/user-assigned managed identity to the Azure-hosted GitLab runner. Hosted runners without Azure MI access cannot use `az login --identity`. Protect runners, branches and CI variables; untrusted jobs must not access this MI. Set `AUDIT_STORAGE_ACCOUNT`, `AUDIT_SUBSCRIPTION_ID`, optional `AUDIT_MI_CLIENT_ID` (client ID, NOT principal ID), optional `AUDIT_CONTAINER` (default audit), `AUDIT_ENVIRONMENT`, `AUDIT_MODULE`. `AZ_CSP_TYPE` must be the Azure CLI cloud name (existing pipeline setting). Reviewer MI needs the reader role and network access.
3. Runtime image must contain Bash, Terraform, Azure CLI supporting `--client-id`, Python 3. Existing infrastructure SP variables and mirror access remain required. Publish all template files to the referenced GitLab `dev` ref or pin every include consistently to a reviewed commit. Verify merged CI configuration with the private GitLab CI lint API and a real consumer's `examples/basic` configuration.
4. GitLab's keep-latest-successful-artifacts setting can retain artifacts past 90 days. Disable it if strict expiry is required. Restrict artifact download access: plans/output can contain sensitive values.
5. Obtain S010 and legal approval. There is no lock command or lock toggle in this implementation. After approval, use a separately reviewed change and authorized operator to lock retention, reconcile Terraform configuration/state, and archive approval evidence. Locking cannot be undone.

## Query

Run using a reviewer MI from an authorized Azure host. Set `CI_PROJECT_DIR` to a writable working directory plus the audit variables above:

```sh
python3 scripts/audit.py query --environment dev --module group/module --actor alice --start 2026-10-01T00:00:00Z --end 2026-10-31T23:59:59Z
```

Returns matching JSON records as JSON lines. Dates are inclusive timezone-aware timestamps. The tool lists all `records/` blobs (Azure CLI pagination enabled), downloads and filters locally; it is deliberately a simple low-volume query tool, not an indexed analytics service. Query errors fail visibly.

## Verification

Run `python3 -m unittest discover -s tests -v`, `terraform fmt -check shared-services/audit`, and backend-free Terraform init/validate. Local automated tests mock Azure/Terraform: they do not prove cloud access or WORM enforcement.

After legal approval, run `bash scripts/verify-worm.sh` ONLY on an already-locked approved test container, using an operator with data write/delete rights. It checks actual immutability error codes, refusing an unlocked policy and rejecting unrelated authorization/network errors. It never locks a policy. Its uniquely named evidence blob remains retained for the full policy duration. Production deployment, failed/successful live pipeline acceptance, cancellation reconciliation, Azure overwrite/delete rejection, and private GitLab CI lint remain environment-dependent acceptance work.
